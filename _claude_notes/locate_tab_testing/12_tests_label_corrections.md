## What this session was for, and why it is worth a screen

`geometry.json` has been carrying the extraction's **own** list of doubts since the sheet was indexed
on 2026-08-03 — `pages[0].review_queue`, **278 items**, each with a box round it and a confidence.
**Nothing had ever read it.** The file even says why there are so many, in a field of its own:

> `text_source`: *"OCR of stroked glyph geometry — this PDF has no embedded font text, so every
> label must be verified with the vision pass."*

There is no font in this PDF. Every string on the sheet was read off the *shapes of the strokes*, and
**30 of the 70 printed net names came back at confidence 0.4.**

That is not cosmetic. It is the thing that limits the whole wires-and-nets project. Phase E ranks
candidate conductors by comparing a run's printed net name against a wire's net id, and **only 17 of
26 nets match a printed conductor group today.** Nine of the nine misses are misreads:

| Read as | Almost certainly | Why |
|---|---|---|
| `LI-A`, `LI-A1` | `L1-A`, `L1-A1` | capital I for the digit 1 |
| `TINSP1`, `TINSP2` | `IINSP1`, `IINSP2` | |
| `DINSP1`, `DINSP2` | probably the same pair | |
| `130.`, `OV.` | `130`, `0V` | trailing ink taken for a full stop |
| `"GND` | `GND` | |
| `C4E-1` | `24E-1` | and `24E-1` is read correctly in fifteen other places |

Correcting these is **not repairing the index.** The netlist is already right — 26 nets, 131
terminals, no twins, and `L1-A` against `L1-A1` is two real nets with a circuit breaker between them
rather than one string read twice. What is wrong is a layer *below* the netlist, in strings that
never became entities. **T-740 is the test that this stays true.**

## The vocabulary, in one place

The screen is a queue of **readings**, and there are two kinds because there are two id spaces.

| | A **string** | A **run** |
|---|---|---|
| id | `T0012` | `C0030` |
| what it is | one text label the OCR pass lifted off the paper | one polyline of conductor the vector pass lifted out of the PDF |
| its reading is | its text | the **net name printed beside it** |
| how sure | a confidence, 0–1 | **none** — a net name was *bound* to it or it was not |
| how many | **515** | **149** |
| flagged | 159 | 119 |

**664 readings, 278 of them flagged.** A run has no confidence because its name is not a guess: the
extractor either found a label beside it or it did not, and for **79 of the 149** it did not. That is
a blank rather than a mistake, which is why the queue sorts the two apart.

Three more words the screen uses:

- **net name** — a badge. It means *a run's net name depends on this reading*: every run, plus the
  **70** labels a run's name is lifted from. This is the set Phase E reads and nothing else moves it.
- **was** — what the machine read, kept forever. `geometry.json` is regenerated by a re-extraction
  and would take the original with it, so this is the only durable record of what it actually saw.
- **not a label** — `text: null` in the file. Some of what the extractor found beside a conductor was
  never a name at all, and no string can say so.

**This is the half of the decision that says "editing all of them should be possible", and it is not

## T-730 · **Reset deletes the decision — it does not write the machine's reading in**

**This is the one assertion in this document worth reporting loudly.** It is invariant 10 in a third
set of clothes, and T-570 is the same test about an end label's side.

**Expected.**

1. the box goes back to **`BLACK 22 AW6`**, the machine's reading;

3. the header count drops by one;
4. and in the file, **the `T0300` key is gone.** Not `{"text": "BLACK 22 AW6"}` — *gone*.

**Do.** Confirm it:

    cat schematic_extraction/PS20115MLM4-2/extracted_docs/label_corrections.json

**Why this matters more than it looks.** If Reset wrote the reading back in, the file would say
*somebody decided this reading is right* about a row nobody had looked at. The file's entire job is
to distinguish **nobody has looked at this** from **a person decided this**, and a default stored as
though it were a decision destroys exactly that. Absence *is* the answer.

**Do.** Now the opposite. On a row you have **not** corrected, press the **✓** button without
changing the box.

**Expected.** The row says **`confirmed`** and the file gains
`{"text": "…", "was": "…"}` with the two the same.

**And that is deliberately kept**, which looks like a contradiction of the paragraph above and is
not. The distinction is worth being exact about:

- an end label's **side** would have been computed anyway with nobody looking, so storing it destroys
  information;
- **nothing produces *a person checked this* but a person.** A low-confidence reading somebody has
  verified is new information, and the queue's whole job is to get smaller.

**Do.** Now check the safety rail. Click into three boxes in a row without typing anything, tabbing or
clicking away each time.

**Expected.** **Nothing is recorded.** Blur alone is not a decision, or scrolling the queue would
sign all 278 readings on the way past. Saying *the machine was right* takes the **✓**.

**Do.** Press **↺** on a row with no decision.

**Expected.** The button is **disabled**. There is nothing to take back.

## T-745 · The `kind` badge now agrees with what you typed

**Do.** Switch to **`All readings`** and find **`T0463`** — the second printed `125` at the far
right of that run. Its badge says `text`, because `125,` with a trailing comma matches no rule the
extractor has.

**Do.** Type `125` and press `Enter`.

**Expected.** The badge changes to **`net_number`**, with a small `·` after it, and its tooltip says
the word was worked out from the text you typed and what the extraction had called it before.

**Do.** Hover the badge on a row you have **not** corrected.

**Expected.** It reads exactly what the extraction said, and its tooltip says so.

**Why this is the whole of that problem, and there is nothing to author.** `kind` is a **pure
function of the text** — `classify_label()` in `schematic_skills/scripts/extract.py` — and nothing
on the server or the client branches on it; `ink.py` calls it *"a hint for the reader, never a
filter this server applies"*. You asked three separate times for a way to edit that field. The
honest answer is that there is no field: the badge was simply not being recomputed, so it went on
describing a string you had already replaced. A badge that disagrees with the box beside it reads as
a field you are not allowed to correct, which is exactly how it was reported.

**The one thing worth knowing about the fix.** The classifier is mirrored in TypeScript, because the
original imports PyMuPDF and exits without it, so neither the server nor the browser can import it.
Two copies of a rule can drift — so an **uncorrected** row shows the extraction's own answer,
verbatim, which cannot drift because it *is* the extraction's answer, and the mirror is consulted
only where you have changed the text. `review/model.test.ts` pins it against a table of 45 strings
generated from the Python, which is what will say so if `classify_label` ever changes.

## Hand-editing, and what happens if you get it wrong

The file is a text file and being readable by a person is the point. Two cautions, both the same
shape as `locations.json`'s:

- **the screen holds a whole-document draft**, so a hand edit made while the tab is open will be
  overwritten by that tab's next save (`H1`/`K2`, in a second file now);
- **a correction keyed on an id that is not on this sheet draws nothing and is refused by name.** Add
  `"T9999": {"text": "L1-A"}` by hand, reload, and the red strip says

      label_corrections.json corrects 'T9999', which is not a label or a conductor in geometry.json

  That refusal exists because it is the one mistake here whose symptom would otherwise be *nothing at
  all* — never applied, never drawn, never mentioned. It is the same reasoning as `H14`.

One typo costs one reading and nothing else: put a number in a `text` and that entry is refused with
its id in the strip while every other correction is kept.
